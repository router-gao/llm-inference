# Spark Zero｜创意原点

> 第一轮头脑风暴：让 AI 从陌生术语，变成看得见、点得动、讲得清的故事。

整理日期：2026-10-05。来源：本轮对话的主题归纳，并非逐字聊天记录。记录两个项目的共同起点，保留问题、意图和边界，不把所有想法自动变成开发承诺。

## 最初的火花

从新建 `llm-inference` 仓库开始，我们想做基于 HTML 的学习材料：简单易懂，通过鼠标点击推进推理步骤，从不同角色视角理解同一件事。读者不需要先读论文，也不需要先懂 GPU。

后来，文生视频的创作属性带来第二条方向：让普通人先被作品与故事吸引，再理解技术。它独立为 Omni Canvas，并进一步纳入文生图。

## 为谁而做

LLM 学习项目面向思科客户、合作伙伴、销售和售前工程师。很多读者有网络和 IT 背景，日常维护网络、虚拟化和云，却没有大模型或 AI 背景；也要照顾对技术兴趣不高的销售和非 IT 访客。

表达从读者的问题出发：发生了什么？为什么要这样做？需要哪些资源？出了问题怎么判断？最终用户会感受到什么？首页要初学者友好、寓教于乐，不能像学术论文或技术手册。

## 第一条主线：一次酒店预订背后的世界

用户要求在某个时间预订某个酒店。通过可点击的步骤，展示最终用户、智能体、大模型和 AI Infra 工程师各自看到的流程：澄清时间与地点、查知识和实时库存、调用工具、处理失败、确认与执行。说明智能体如何组织任务，以及为什么一次用户任务可能包含多次模型调用。

这是教学模拟的第一版方向：中文、无需后端，不接真实酒店或模型 API。模拟必须明确标识，不能把演示说成真实预订。

## 把常见词讲清楚

- 推理过程：Token、Prefill、Decode、QKV、KV Cache；特别区分 QKV 计算和 KV 缓存的资源需求。
- 工作指标：并发、请求速率、吞吐量、首字符显示延迟、首 Token 延时、Token 间隔、每输出 Token 时间、端到端延迟、分位数与服务目标。解释计时起止、单位与用户感受。
- 模型参数：稠密与稀疏模型、MoE、总参数与激活参数、维度、向量、矩阵、张量、shape、层数、隐藏维度、注意力头与精度。

术语不是孤立词典：首次出现就解释，并与场景、资源和体验联系起来。

## 从一张卡到一个集群

我们提出了这些实际部署问题：

- 一个模型在一张 GPU 上，多用户怎样 query？队列、批处理、输入输出长度怎样影响并发？
- 一个模型在一台服务器的多张卡上，数据怎样通信？
- 一个模型跨多台服务器，卡间通信怎样组织？
- 一台服务器或一个资源池部署多个模型，GPU 怎样分配？服务器、资源池与 Kubernetes Pod 的边界需要澄清。
- 部署 GPU 时怎样估算需要多少卡？权重、KV Cache、临时资源、余量与目标体验如何共同决定容量？

不能只问“显存装不装得下”，还要问排队、延时、吞吐、资源争用和故障时会发生什么。单机多卡、多机通信与模型副本要分别解释。

## GPU 与网络：熟悉的 IT 世界怎样接上 AI

已提出的内容包括：

- GPU 的起源、基础架构和代际变化。
- 思科 UCS 支持哪些 GPU、具体平台和条件是什么；比较显存、带宽、算力与精度、互联、功耗等参数，并解释高低如何影响生产部署与用户体验。
- NVIDIA 与 AMD 的区别，以及与 TPU 的比较；硬件之外还包括软件生态、兼容和部署条件。
- 虚拟 GPU、资源共享、Kubernetes 使用 GPU 的原理。
- GPU 机内与跨服务器通信，RDMA、RoCE、DPU；把 AI 网络知识与读者已有网络经验连接起来。
- 思科特色 AI 网络：先预研，输出报告，再讨论哪些内容进入课程，不直接把所有产品介绍纳入实现。
- NVIDIA 认证考试与继续学习路径。

型号支持、规格、考试状态与性能结论需要有日期和依据，峰值参数不能冒充实际体验。

## 知识库、RAG 与微调的探索

RAG 要展示两条完整流程：离线文档处理、切分、Embedding 与索引；在线查询、Embedding、检索、Reranker、上下文组织、生成与引用。

用户已有思科离线知识库，约几千页；还有中兴与华为资料，两万多页。提出的问题是：能否用来微调？能否做微调 Demo？

这属于预研候选。先研究数据格式、质量、版本、许可、目标与 GPU 条件，再比较 RAG 和微调路径。页数本身不能证明训练收益或资源需求；目前没有执行训练，也没有承诺训练效果。

## 从真实 Demo 接近代码

用户以前做过识别车辆颜色和型号的 GPU Demo，希望纳入课程，并介绍 PyTorch 与源代码。教学应连接输入、预处理、张量、模型推理与结果。

原 Demo 的代码、权重和运行说明尚未提供。后续独立教学样例不能冒充用户原 Demo 的复现。

## 第二条主线：Omni Canvas

文生视频独立成项目，有自己的首页与直接可访问的 GitHub 页面目标。用户后来手动创建 `router-gao/omni-canvas`，授权文生视频和文生图内容放到这里。

### 视频技术与产业想法

重点希望介绍 Seedance 云端与本地模型，两者各有长处；研究本地部署配置、云端与本地如何配合。进一步探索文生视频产业：哪些国家发展较好、为什么、如何扩展中东、场景怎样复制，以及中国脚本如何适配好莱坞、中东和印度。

这些产业与跨文化议题先做预研，再共同讨论范围，不预设国家排名、市场结论或所有功能必须实现。

### 面向当地人的首页

首页要炫酷、吸引普通人，不能只是技术入口。中东页面以阿联酋、迪拜语境为重点，目标是让当地人喜欢，而不是让亚洲人想象中的“中东风格”占主导。

已明确要求阿拉伯语与英语切换，阿语支持从右向左排版。随后另做中文页面，使用中国元素；中国页面可以后置，但必须保留在需求与排期中。

曾生成的三个视觉探索没有被选定，也不代表最终设计获批。当前旧中文概念原型不代表中东双语或后续中国页面完成。

### 文生图的新起点

文生图已加入 Omni Canvas 的需求记录。模型、服务、场景、云端与本地路径，以及是否连接视频关键帧流程，都需要预研与review；本轮没有启动文生图实现。

## 我们约定怎样推进

项目按软件开发流程管理，先组队、明确角色与任务，重要需求和人员分工文档由用户review。职责覆盖产品、内容与推理、基础设施、体验与前端、质量，以及主代理的协调。

- 正式需求要完整体现所有明确要求，并在排期与任务中可追踪。
- 另设快速灵感文档：随时记，不要求技术可行，不等同正式需求。
- 大需求先预研，输出需求或功能预研文档，再讨论取舍。
- 遗留问题进入台账，周期性讨论；维护 release notes。
- 提供 HTML 格式需求阅读版，便于review。
- **收到新要求先记录，不自动开始设计或实现。** 先整理、预研和review，再按用户指示进入下一阶段。
- GitHub 内容推送、网站部署、需求确认和功能完成分别记录，不能混称“发布完成”。
