# AI Infra 教学与容量规划规格

当前读者定位：有网络与IT背景、缺少AI背景的思科客户、合作伙伴、销售及售前工程师；按[读者规范](../product/audience.md)组织基础与工程解释。此前宽泛的读者称呼以本条为准。

负责人：AI Infra 教学与容量规划角色。状态：首版教学设计，待技术审校。面向需要理解业务体验与部署取舍的Cisco客户、伙伴、销售和售前。以下容量与通信演示均为教学估算，不能冒充实测性能或采购建议。

## 1. 读者首先要回答的问题

读者从“同时有 20 人让助手预订酒店”进入，而非从矩阵公式进入。每个请求先读取输入（prefill），再逐个生成输出（decode）。预订涉及多次模型调用和工具等待，因此 20 个酒店任务不等于 20 条始终运行的模型序列。展开详情才展示 token、KV cache、batch 和并行策略。

每个章节默认包含：一句直觉、可点击的请求/GPU/通信动画、当前资源状态、为什么等待、工程细节折叠框。动画可暂停、单步、重置；颜色之外使用文字和图标解释状态。

## 2. 单卡上的一个模型怎样服务多人

类比：GPU 是厨房，模型权重是常驻设备，请求是订单，KV cache 是各桌已经备好的材料。多个用户通常共享同一份权重，但各自保存独立的请求状态和 KV cache。共享权重不意味着请求信息混在一起。

交互步骤：请求入队 → 调度器选入可运行批次 → prefill → decode 一步 → 已完成请求离开、新请求加入 → 显存不足的请求继续等待。展示 continuous batching 的含义：每一步可改变参与的序列，而不是必须等整个批次全部结束。

必须解释三种不同数量：正在进行的业务任务、模型服务里的排队请求、正在执行的序列。工具等待期间可以释放执行槽位；KV 是否保留取决于服务和调用方式。不要画成“用户数 × 模型权重”。

参数：输入 token、输出 token、请求到达速度、同时运行序列上限、可用 KV 预算、prefill 调度策略。观察量：队列长度、首 token 等待、输出节奏、请求完成时间、KV 占用。吞吐和延迟数值由明确声明的模拟服务时间决定，禁止标成真实 GPU 测评。

## 3. QKV 与 KV cache：资源到底留给谁

Q（query）、K（key）、V（value）是注意力计算里的向量；Q 不是用户发来的自然语言 query。一次生成时，当前 token 的 Q 与历史 K/V 参与计算。普通自回归推理通常缓存历史 K 和 V，而不是把所有历史 Q 长期缓存。KV cache 随活跃序列数和累计 token 增长。

权重里的 Q/K/V 投影参数归入模型权重；计算中的 QKV 张量、激活和临时 attention workspace 归入执行开销；历史 K/V 归入 KV cache。三者不能重复计算。GQA/MQA 的 KV heads 数可以小于 query heads 数，应以模型配置为准。

教学公式（单序列、未分片、标准 KV 存储）：

`KV_bytes = 2 × layers × kv_heads × head_dim × cached_tokens × bytes_per_KV_element`

批量预算是各活跃序列 cached_tokens 的总和，再考虑块式分配的向上取整、元数据和安全余量。共享前缀、滑动窗口、KV 量化及不同并行策略会改变结果。TP 下实际 KV 分片或复制取决于实现和 heads 划分，不能一概用 GPU 数量直接相除。

教学例子：32 层、8 个 KV heads、head dimension 128、BF16（2 bytes），每 token 为 128 KiB；一个 8192-token 序列约 1 GiB，16 个这样的独立序列约 16 GiB（尚未加入分配开销）。将 KV heads 切换成 32，结果变成四倍。例子是配置演算，不代表某个型号的实测服务。

资源设计按钮：限制输入/输出长度、限制活跃序列、预留 KV 池、量化 KV（需评估质量与内核支持）、复用公共前缀（注意隔离策略）、排队/限流/拒绝、回收结束序列。用户可以观察哪一项缓解显存、哪一项改变体验。

## 4. GPU 数量怎样估算

先明确目标：模型/量化格式、最大上下文、并发、首 token 延迟、输出 token 延迟、请求到达分布、可接受排队、冗余要求。GPU 型号的可用显存与互联也是输入。

教学显存账本：`总需求 ≈ 权重 + KV + 激活/执行 workspace + 运行时/通信开销 + 分配碎片 + 预留`。权重粗估 `参数量 × 每参数字节数`，低比特量化还需 scales、zero points、未量化层和对齐，不能只按位宽得出精确文件大小。激活、图捕获与 workspace 必须通过具体框架/批次配置验证。

理想均匀分片的 `ceil(总需求 / 每卡预算)` 只能作为“显存容纳”的粗略下界，且必须注明均匀分片假设。某些缓冲区会复制、PP 阶段可能不均衡、KV 分片受实现限制，所以应进一步展示每卡账本并检查最满的一张卡。

例子：假设 8B 模型 BF16 权重约 16 GB（十进制），KV 为 16 GiB，其他开销与预留合计 8 GiB，则约 38.9 GiB 的预算只能说明在该假设下是否容纳；不能推出每秒多少请求。页面统一显示单位，并说明 1 GiB = 2^30 bytes、1 GB = 10^9 bytes。

吞吐需要实测 prefill/decode、内存带宽、算力、通信、调度和真实长度分布。确定每副本在延迟目标内可承受的到达率后，再估算副本数，并考虑峰值、故障冗余和余量。展示“显存够用但延迟超标”的反例。动态批量提高利用率的同时可能增加排队；长输入可影响短请求的首 token 延迟。

## 5. 一台服务器多卡与多台服务器

| 布局 | 直觉 | 典型通信 | 必须解释的取舍 |
| --- | --- | --- | --- |
| 单卡模型、多副本（DP） | 多个完整厨房分别接单 | 请求路由；通常无每 token 跨副本同步 | 增加总服务容量；不自动加快单个请求；每副本都占权重与 KV |
| 张量并行（TP） | 每层计算由多位厨师共同完成 | 层内 collectives，例如 all-reduce/all-gather，具体取决于实现 | 模型可分摊；通信往返与带宽可能主导小批次 decode |
| 流水线并行（PP） | 不同卡负责不同工序/层 | 阶段间传激活 | 阶段负载和流水线空泡影响利用率；不能直接认为卡数越多越快 |
| TP/PP 加多副本 | 每个厨房内协作，再开多个厨房 | 副本内通信与副本间路由 | 同时管理单请求容量和总体吞吐 |

交互可在 1 卡、单机 4 卡、两机各 4 卡之间切换；点击 token 显示它经过哪些卡、哪些边界发生通信、谁在等待。策略不支持或显存放不下时，显示具体原因。教学拓扑参数不能伪装成真实硬件带宽。

单机：GPU 通信可能经过 PCIe，具备支持时可使用 NVLink/NVSwitch。是否可用取决于 GPU、主板拓扑、驱动和软件，不是“同服务器就有 NVLink”；GPU peer access 也需实际验证。

跨机：GPU 依赖网络适配器与交换网络，不是普通单机 NVLink 自动延伸。RDMA 是远程直接内存访问能力；InfiniBand 是一种可提供 RDMA 的网络技术；RoCE 是以太网上的 RDMA。GPUDirect RDMA 在硬件、驱动与拓扑支持时允许 NIC 直接访问 GPU 内存，减少 CPU 中转，不表示零成本或无配置。

RoCE 教学强调拥塞控制、ECN/PFC 等依部署而定的配置、网络隔离、MTU 与拓扑；不能宣传“打开 RDMA 就更快”。NCCL 等通信库根据支持与配置选择传输。可点击“NIC/交换机/CPU 中转”观察通信路径和瓶颈。通信简化模型 `时间 ≈ 消息字节 / 有效带宽 + 启动延迟` 仅用于单条消息直觉；collective、拓扑与拥塞不能直接套这个式子算真实端到端速度。

## 6. 一个服务器部署多个模型怎么分配

先澄清术语：物理服务器（节点）可以运行多个 Kubernetes Pod；Pod 是部署/调度单元，可以含多个容器，不是物理服务器的别名。通常申请整数 GPU 的 Pod 获得由 device plugin 分配的设备，跨 Pod 共享需要显式支持与配置。

| 方法 | 读者理解 | 边界 |
| --- | --- | --- |
| 独占整卡 | 一个模型服务占一张或多张卡 | 易于预算和隔离，但低负载可能闲置 |
| MIG | 支持的 GPU 切成具有固定资源的实例 | 型号、profile 与互联支持有限；模型必须适合实例预算 |
| Time slicing | 多个工作轮流使用设备 | 不是显存硬隔离或吞吐保证，仍有争用与 OOM 风险 |
| 多进程共享 / MPS | 多个服务在同卡执行，MPS 可改善部分执行并发 | 不等于 MIG 的内存/故障隔离；需框架兼容、预算与压力验证 |
| 动态装卸模型 | 用时间换容量，按需加载/卸载 | 加载延迟、冷启动和缓存抖动需要显示 |

交互放置模型：主模型、embedding 模型、reranker 各有权重/峰值 KV 或执行内存、调用频率与延迟优先级。读者拖到 GPU 后显示预留账本、空闲余量、竞争和加载时间。Embedding/reranker 的开销按实际架构处理，不把所有模型都套生成模型长期 KV 公式。RAG 中可能串行或并行调用，不可假设“模型各占一张卡”或默认同时达到最大负载。

## 9. GPU 代际变化：升级后究竟改变什么

新增用户要求：涵盖GPU代际变化。读者问题不是“型号年份背下来了吗”，而是“为什么同一模型换卡后容量、首token等待、生成节奏、并发和通信表现可能不同”。本节为内容规划，具体规格与性能数据尚未核验。

### 分层解释

基础层用“工作台大小、取材料速度、计算速度、协作通路、耗电与散热”分别解释显存容量、显存带宽、算力、互联及部署条件。工程层再展开架构、Tensor Core、精度、内核和网络。不能把代际、产品型号和服务器配置当成同一件事。

| 比较项 | 为什么影响推理 | 不能直接推出的结论 |
| --- | --- | --- |
| 显存容量 | 决定权重、KV与运行开销能否容纳，以及可预留多少活跃序列 | 新一代所有型号都比旧卡显存大 |
| 显存带宽 | 常影响权重/KV搬运成本；小批量decode可能受它制约 | 峰值带宽提高多少，所有场景就快多少 |
| Tensor Core与计算能力 | 支持不同矩阵计算精度和吞吐，影响prefill等计算工作 | 峰值FLOPS等于实际tokens/s；不同精度的峰值可直接横比 |
| FP16/BF16/FP8/FP4等支持 | 可能减少数据占用、改变计算性能 | 硬件支持就代表模型、框架、量化方法和内核可直接使用，或质量无损 |
| NVLink/NVSwitch与PCIe拓扑 | 改变机内模型分片的通信成本 | 同代卡或同服务器必定具备同样互联 |
| NIC、RDMA与跨机网络 | 决定跨机通信路径及有效带宽 | 换GPU就自动升级网卡和交换网络 |
| 功率、散热与机箱形态 | 决定机房、电源、散热及部署能否支持 | 新卡可直接替换旧服务器里的卡 |
| 软件和硬件兼容 | 驱动、CUDA、推理引擎及内核需支持对应设备 | 老环境无需变更即可发挥新硬件能力 |
| 成本与供给 | 影响达到服务目标的总体成本 | 最新卡必定最划算；仅卡单价等于服务成本 |

### 代际地图与型号关系

NVIDIA作为第一条教学路线，选择Volta（V100）、Ampere（A100）、Hopper（H100/H200）与Blackwell（如B200）作代表性候选。它们是架构与产品关系示例，不是完整产品史或“最新型号”声明。H100与H200属于同一架构代际的不同产品，不能把每个新型号都叫新架构。A100、H100等还需区分显存容量、PCIe/SXM等形态与服务器拓扑。

GB系列系统名称等涉及CPU/GPU与平台组合，不能和单颗GPU规格混比。消费级与数据中心GPU也要区分显存、互联、可靠性及软件支持。AMD等路线作为后续对照内容，采用相同比较维度，不把GPU推理等同于单一厂商。

发布具体代际图前，按官方产品与架构资料记录型号、形态、发布日期口径、显存容量/带宽、计算精度、互联、功耗、规格来源与核验日期。没有核实的参数显示待核验，不凭印象填写。规格表避免跨精度、稀疏/稠密峰值或单卡/整机单位混比。

### 可点击演示

1. 保持同一模型、输入输出长度、并发及延迟目标，切换GPU配置。
2. 分别查看权重、KV、临时空间和预留是否容纳；配置变化重新计算每卡账本。
3. 点击prefill、decode、机内通信、跨机通信，查看当前可能的瓶颈与适用条件。
4. 切换精度时说明量化、质量评估和软件支持要求，不能只改每参数字节数便声称完成部署。
5. 比较“单张新卡”和“多张旧卡”的容量、通信、冗余与成本权衡，不自动推荐其中一项。

只有规格支持时展示容量推算。没有工作负载实测或经解释的模拟模型时，不为各代GPU虚构tokens/s、TTFT或升级倍数。所有时间与吞吐示意需明确固定教学假设。
