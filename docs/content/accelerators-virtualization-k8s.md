# 加速器选择、虚拟GPU与Kubernetes GPU原理

状态：新增设计初稿，待用户review与官方来源核验。目标读者具有网络、虚拟化和云维护经验，没有AI基础。解释机制和取舍，不给未经验证的产品性能排名。关联REQ-11/13/15/16。

## 1. NVIDIA、AMD与TPU：比较的是完整部署路径

这里的“显卡”聚焦模型推理所用加速器。消费级显卡与数据中心GPU分开；同厂商不同型号和代际也不能一概而论。

| 比较项 | NVIDIA GPU | AMD GPU | Google TPU | 对生产和体验意味着什么 |
| --- | --- | --- | --- | --- |
| 设备定位 | GPU产品线，数据中心/消费级等不同定位 | GPU产品线，Instinct等加速器与消费级产品不同 | 面向机器学习的专用加速器体系 | 都需匹配模型与负载，不能仅按“AI芯片”名称判断 |
| 软件栈 | CUDA生态，具体框架/内核/设备支持需核验 | ROCm生态，支持型号、系统与框架需核验 | 常见通过XLA等编译栈，JAX/框架路径与运行平台需核验 | 模型是否能跑、优化是否成熟、团队维护成本可比峰值更重要 |
| 计算与存储 | 精度、显存/带宽、矩阵能力依型号 | 同样依型号，不能用品牌替代规格 | 内存、计算精度与拓扑依代际/平台 | 影响模型容纳、prefill/decode和并发，静态规格不等于tokens/s |
| 多设备互联 | NVLink等机内机制和网络通信依平台 | 设备互联和网络路径依产品/平台 | TPU系统有自身互联与切分方式 | 分布式策略和通信路径不能照搬，需同负载实测 |
| 部署获取方式 | 支持的本地服务器或云实例 | 支持的本地服务器或云实例 | 本课程聚焦Google Cloud TPU；其他形态另行区分 | 采购、区域、配额、运维控制与数据要求不同 |
| 移植和优化 | CUDA相关自定义算子可能形成依赖 | 需确认替代内核、算子及兼容路径 | 编译、形状与模型实现可能需适配 | 从能启动到达到质量/性能目标需要独立验证 |

TPU不是虚拟显卡，也不是GPU的一个品牌型号。专用设计不保证任意LLM比GPU快或便宜。AMD不应被描述为“NVIDIA换个驱动”，CUDA/ROCm/XLA也不是三种物理芯片。

选择流程：确定模型与精度→核实框架/算子/量化路径→检查容量与互联→按相同输入输出分布和SLO压测→比较合格吞吐、错误率与总成本→考虑可运维性。比较时固定或说明差异：型号/代际、模型版本、精度、软件、并行、batch、长度与价格时点。具体UCS支持清单仍以Cisco型号资料为准；TPU云平台不应出现在UCS可安装GPU列表里。

## 2. 虚拟显卡：先分清用途与机制

| 机制 | 做什么 | 隔离与运维取舍 |
| --- | --- | --- |
| 虚拟显示适配器 | 给虚拟机提供显示设备接口 | 不等于提供真实GPU模型计算能力 |
| GPU PCIe直通 | 将物理GPU等设备交给虚拟机使用 | VM直接使用设备，需IOMMU/平台支持；迁移、共享与故障恢复依实际方案 |
| vGPU | 用厂商支持的方式向VM等呈现虚拟GPU，可能依时间共享或硬件分区实现 | 型号、profile、驱动/管理器、hypervisor及许可需核验；不统一保证隔离/迁移/性能 |
| MIG | 支持设备上的硬件资源分区机制 | 可在支持组合中与虚拟化结合，但MIG不等于所有vGPU方案 |
| Time slicing / MPS | 时间共享或受支持的执行并发机制 | 不等于显存硬隔离；与VM虚拟设备层不是同一概念 |

VM里的GPU也需要正确驱动与模型运行栈。不能按普通vCPU超配经验，假定GPU显存可以安全无限超配。规格中的“可分配显存”不代表独立等比例算力；邻居负载、profile、共享策略和上层调度影响尾延迟。

交互：物理GPU→直通或支持的vGPU层→两台VM→各自模型，点击显存/执行资源/驱动与隔离边界。对比独占和共享、邻居负载、实例重启；迁移支持明确待核验，不展示为普遍能力。连接用户体验：资源争用会排队或出字不稳，隔离成本与利用率之间需要取舍。

## 3. Kubernetes如何使用GPU

Kubernetes通常不直接执行CUDA/ROCm算子，也不自己拆分模型。它负责调度和设备资源分配，模型服务器负责请求调度与推理。

### 标准设备插件路径

1. **节点准备**：安装兼容驱动和容器运行支持，验证设备可用。若节点是VM，底层直通/vGPU支持须先成立。
2. **发现并发布资源**：厂商device plugin向kubelet注册，报告可用设备及健康状态；常见扩展资源名如`nvidia.com/gpu`、`amd.com/gpu`，具体以插件配置为准。
3. **Pod声明资源**：标准整GPU扩展资源通常使用整数limits；requests未设置时通常按limits处理，若同时设置则需相等。其他共享/分区资源采用实际插件定义，不能自行写0.5表示半张普通GPU。
4. **scheduler选择节点**：依据可分配资源和约束选节点；它通常不会根据模型8B/70B或实际显存自动估算需求。单个Pod一般不能跨节点拆成多机模型。
5. **kubelet与插件分配设备**：插件提供设备访问所需信息，结合运行时/CDI等受支持方式交给容器；应用使用被分配设备执行。
6. **模型服务启动**：加载权重、准备缓存和内核；readiness应该等到可服务请求，不仅是容器进程启动。
7. **接请求与监控**：服务路由与推理引擎处理batch、队列、KV；节点/设备和应用指标一起监控。结束Pod后资源可重新分配，但活跃请求与KV不是自动迁移。

例如Pod声明`nvidia.com/gpu: 1`通常请求插件发布的一个资源单位，不等于“任意一张显存足够的卡”，也不能跨插件共享机制统一解释为独占物理整卡。标签/亲和性帮助匹配型号，具体拓扑和分区语义由配置确认。

### 进阶但重要的边界

- GPU Operator等工具可管理部分驱动/插件/监控生命周期，但属于额外生态，不是Kubernetes自动自带能力。
- DRA等设备分配机制作为版本相关扩展，核验Kubernetes版本、驱动和支持状态；不混同传统device plugin流程。
- MIG、时间共享和vGPU需底层与插件显式支持。调度资源单位不自动成为硬隔离保证。
- GPU使用率低不代表可以立刻给另一个Pod；资源预留、实际显存、共享策略和SLO要一起检查。
- 模型副本扩容与TP/PP多机部署不同；后者需框架协调、拓扑/网络及必要调度机制，不能简单增加副本数。
- 使用队列、长度、TTFT和合格吞吐等业务指标规划扩缩容；只看CPU指标可能失真。模型冷启动、GPU供给和副本ready延迟需要考虑。
- 安全与多租户：设备暴露、权限、故障域和监控按具体方案验证，不因Pod隔离就推定GPU强隔离。

## 4. 可点击教学与验收

- 加速器选择：同一模型切换候选软件/硬件路径，显示已核验、待核验或不支持，不生成品牌性能榜。
- 虚拟化：物理设备→虚拟化机制→VM/容器→模型服务，点击资源与隔离边界。
- K8s：Pod声明→Pending→节点选择→分配→加载→Ready→服务；加入无GPU、选错型号、驱动/插件故障和OOM路径，区分调度成功与模型可运行。
- 多机模型：对比多个完整副本与协作分片，解释单Pod单节点与服务跨节点的区别。

M2承接GPU基础与厂商生态概览；M3完成虚拟化、K8s调度和生产案例。验收：能分清芯片、软件栈和部署平台；vGPU/MIG/直通不混同；解释K8s分配设备而推理引擎调度请求；清楚OOM、Pending、加载慢和GPU故障在哪层处理。当前只有设计，示例与测试未实现。
