# AI服务的网络与数据路径 v0.1

状态：新增内容设计，待用户review与技术来源核验。面向有网络、虚拟化与云维护背景、没有AI基础的Cisco客户、伙伴、销售与售前。第一版仍为静态教学模拟，不执行真实配置。

## 1. 从读者熟悉的流量分类开始

| 数据路径 | 传什么 / 为什么传 | 对体验与生产的影响 |
| --- | --- | --- |
| 用户到应用/模型入口 | HTTP等请求、流式输出、认证和路由 | 客户端首字符时间、连接容量、负载均衡及可用性；网络chunk不等于一个token |
| 应用到工具/RAG服务 | 工具参数、检索请求、候选文档与结果 | 完整Agent任务可能主要在等外部服务；不应误判为GPU计算慢 |
| 模型加载与存储 | 权重、模型版本、知识数据与检查点文件 | 启动/扩容耗时、存储吞吐及部署恢复；区别持续decode通信 |
| 同一模型分片间 | TP的collective、PP激活、MoE专家并行的数据交换等 | 参与单次推理的关键路径；通信类型和频率取决于实现 |
| 模型副本间与控制面 | 路由、健康检查、调度、监控等 | 通常无每token副本间同步；副本与模型分片不能混淆 |
| 特定引擎的KV传输 | 分离prefill/decode等部署下传KV状态 | 可能改善阶段资源利用，也增加传输和调度成本；不是所有部署必需 |

学习先区分用户南北向流量、服务间和GPU分片东西向流量，再看共享或独立的管理、存储、业务与计算网络。类别是功能划分，不预设必须部署几张物理网。

## 2. 应增加的网络知识

- **带宽、有效吞吐、延迟、抖动、丢包和尾延迟**：链路标称带宽不等于应用有效吞吐；检查瓶颈链路、扇入和同步等待。
- **拓扑与超售**：机架/跨机架、leaf-spine、ECMP、故障域及uplink oversubscription；示例说明分片跨瓶颈边界的代价，不给无负载依据的通用推荐比例。
- **GPU—PCIe—NIC亲和性**：NUMA、PCIe交换与peer access，影响数据路径；同机设备不代表路径等价。
- **RDMA、RoCEv2、InfiniBand与GPUDirect RDMA**：分别解释能力、协议/网络、直接GPU内存路径及支持条件。对不支持场景展示CPU中转路径。
- **RoCE拥塞与运维**：ECN、端点拥塞控制、PFC、QoS/流量分类、MTU与端到端一致性；解释PFC可带来队头阻塞/暂停扩散，避免把“开启PFC”当完整方案。是否需要哪些机制依据具体平台和设计核验。
- **集合通信**：all-reduce/all-gather/reduce-scatter/all-to-all与点对点，采用“谁传给谁、传什么、谁等待”解释；不让网络工程师先背算法公式。
- **入口与服务路由**：流式长连接、超时、重试、取消、会话/缓存亲和性及副本健康；不能假设轮询路由适合所有模型服务。
- **推理特有部署**：prefill/decode分离、KV传输、MoE专家分布；作为工程扩展，强调收益需压测，非默认最佳配置。
- **安全与隔离**：租户、管理面、业务数据、存储访问和工具权限；网络隔离不能替代应用授权与检索权限检查。
- **可观测性与定位**：阶段计时、NIC吞吐、拥塞/ECN/PFC计数、丢包/错误、collective时间、GPU计算/显存和队列联合分析；指标名称依设备与工具核验。

## 3. DPU：不是“另一块GPU”

DPU通常是面向基础设施数据处理的设备/处理器，结合网络接口、可编程处理核心及特定加速能力。SmartNIC泛指有可编程或卸载能力的网卡；DPU与SmartNIC命名存在厂商差异，不能凭名称断定固定能力。

| 组件 | 主要角色 | 不能据此假定 |
| --- | --- | --- |
| GPU | 执行模型张量运算，存放权重/缓存等 | GPU能替代NIC或自动完成网络安全隔离 |
| NIC / RDMA NIC | 网络收发，支持时提供RDMA等卸载 | 每块RDMA网卡都具有DPU完整处理平台 |
| SmartNIC | 提供可编程处理/卸载能力的网卡类别 | 所有SmartNIC支持相同虚拟化、加密和存储功能 |
| DPU | 可承载网络、存储、安全或虚拟化基础设施处理，依具体设备和软件 | 必须用DPU才能跑LLM；装上就更快；替代GPU生成答案 |

可能的作用：卸载主机CPU的一部分网络/存储处理，承载虚拟交换、隧道、加密、策略或隔离功能，参与存储和遥测路径。必须逐项核验产品、软件、驱动、配置和性能；支持RDMA/GPUDirect也不代表全部数据必然经DPU可编程核心处理。

DPU不是LLM推理的必需组件，也不天然提升token速度。若CPU或基础设施处理是瓶颈，合适卸载可能释放CPU、改善有效吞吐或尾延迟；若瓶颈在GPU计算/显存，DPU未必改变生成速度。隔离、运维职责和安全边界的价值要独立讨论，不能只用tokens/s评价。额外成本、功耗、软件生命周期和故障域也是取舍。

对Cisco UCS的DPU选件、GPU/NIC/DPU组合、驱动和网络拓扑，只依据具体机型官方资料确认。本设计不声称任何候选UCS已支持某款DPU。

## 4. 可点击场景

1. **画清数据路径**：用户请求、RAG、模型加载、GPU通信分别点亮；点击每条边查看载荷、协议类别和体验影响。
2. **DPU开/关对照**：以固定教学假设展示部分处理从CPU迁到受支持卸载路径；同时提供“瓶颈在GPU，出字速度未改善”反例，不输出伪实测倍数。
3. **跨机请求变慢**：查看阶段计时、通信等待、链路与拥塞证据，选择下一检查动作；区分链路带宽不足、拓扑瓶颈与GPU计算慢。
4. **RoCE条件对照**：显示标记、反馈、速率调整和可选暂停的作用及风险；是机制模拟，不给未经验证的交换机配置命令。
5. **prefill/decode分离**：先完成普通部署再展开，显示额外KV传输和阶段调度；与入口请求流量分开。

每个网络/DPU参数按“含义→生产影响→用户体验→适用条件”解释。模拟状态可复位，颜色之外有文字，键盘可操作。

## 5. 排期、验收与核验

M1提供端到端请求/工具/排队路径，M2联动RAG和模型加载；M3完整网络拓扑、RDMA/RoCE、DPU及工程扩展。prefill/decode分离等先进内容属于M3可展开层，不作为理解基础流程的前置条件。

验收：能区分NIC/GPU/DPU、各类流量与瓶颈；解释DPU何时可能有帮助或无助于出字速度；分清RoCE机制、平台支持与配置验证；定位结论有证据、没有GPU型号或协议单因果承诺。DPU不是强制部署部件。
