# LLM、Agent 与 RAG：内容设计与验收草案

当前读者定位：有网络与IT背景、缺少AI背景的思科客户、合作伙伴、销售及售前工程师；按[读者规范](../product/audience.md)组织基础与工程解释。此前宽泛的读者称呼以本条为准。

状态：提案，待项目负责人与技术审校确认。负责人：LLM / Agent / RAG 内容角色。本文是教学规格，不是线上酒店预订系统或 GPU 性能承诺。

## 读者与教学目标

面向有网络、虚拟化与云维护背景、没有AI基础的Cisco客户、伙伴、销售和售前，分层解释：基础层用生活语言讲流程，工程层展开数据结构、状态、资源与失败处理；不要求模型训练背景。先回答“请求去了哪里、谁做决定、数据变成了什么、哪里需要等待、哪里可能出错”，再按需展开术语。每个模块统一使用“用户（user）/ 智能体（agent）/ 模型（model）/ 基础设施（infra）”四视角，与交互设计契约一致；切换时保持同一请求 ID、当前步骤与时间线，让读者看到同一件事的不同层面。正文中的业务侧对应用户视角，应用编排对应智能体视角，推理服务与资源对应基础设施视角；执行者标签可按步骤细分，但不新增视角。

默认中文解释、英文术语可展开。正文先用生活语言，再显示精确定义。每一节应包含可点击流程、输入输出、一步失败分支和一项自测，不要求读者阅读公式才能继续。

## 交互与内容约定

- 上一步、下一步、重置、自动播放 / 暂停均可操作；键盘与鼠标都能选步骤。动画不是唯一信息来源，文字同时说明状态。
- 当前步骤显示：执行者、输入、动作、输出、等待原因、下一步；点击箭头可查看传输的示例数据，敏感字段使用虚构数据。
- 颜色之外使用标签区分“等待 / 执行 / 完成 / 失败”；提供减少动态效果模式。
- 默认运行确定性的本地解释模拟，明确标注“教学模拟，未连接酒店、支付、模型或向量数据库”。真实服务接入是另一个开发范围，不能通过播放动画冒充真实调用。
- 数字、延迟、token 数、检索分数都标注“示例”。浏览器示例不能用来证明真实吞吐、预订成功或模型正确率。
- 用 request_id 关联请求，用 tool_call_id 关联工具调用；前端展示便于理解的摘要，展开后才显示 JSON。

## 模块 A：用户说“帮我订酒店”后发生什么

学习问题：模型为什么不能凭一句话直接完成真实预订？模型、Agent 程序、工具和用户分别负责什么？

示例输入：“帮我预订 2026 年 11 月 12 日入住、11 月 14 日退房的上海外滩附近酒店，两位成人，每晚不超过 1000 元。”所有酒店、价格和库存均为虚构。

| 可点击步骤 | 执行者与输入 | 输出 / 下一步条件 | 画面状态建议 |
| --- | --- | --- | --- |
| 1. 接收意图 | 应用收到用户消息与会话上下文 | 一条带 request_id 的请求；缺少入住日期、人数等则进入追问 | 用户气泡移入应用，缺少字段高亮 |
| 2. 整理约束 | 模型读取消息、工具说明、应用规则 | 候选结构：城市、日期、人数、预算；解释“这只是待验证的提议” | 用户原句与字段卡片连线 |
| 3. 应用检查 | Agent 程序检查日期、范围、权限和字段 | 参数合法才发搜索；不合法返回错误让模型解释或追问 | 参数通过 / 拒绝标记 |
| 4. 查库存与价格 | 获准的酒店搜索工具收到参数 | 真实系统返回可用房型、总价、取消条款；模拟返回固定候选 | 工具泳道亮起，模型泳道等待 |
| 5. 比较候选 | 模型读取工具结果与用户偏好 | 给用户推荐与理由；无法确认的内容明确说明 | 三个候选卡片及依据 |
| 6. 用户确认 | 用户选择具体酒店、房型、总价与条款 | 可审计的确认记录；更改日期或价格则重新确认 | “待确认”闸门挡住预订箭头 |
| 7. 应用执行预订 | Agent 程序再次检查库存 / 价格，使用授权工具；使用幂等键 | 订单号或结构化失败；价格变化、售罄、超时进入异常分支 | 工具请求与返回分开显示 |
| 8. 告知结果 | 模型 / 应用读取订单状态 | 仅有成功工具结果才说预订成功；超时状态未知先查询订单，避免重复提交 | 订单状态与最终答复对照 |

支付、个人信息与登录不是模型天然拥有的能力：应用通过受控接口、权限与安全流程提供能力。模型提出工具调用，Agent 程序决定是否允许执行。模型生成“已预订”的文字不会创建订单。确认要求是本教学应用的产品约定，不意味着所有 Agent 都默认具备确认机制。

可点击异常：缺少日期 → 追问；搜索无结果 → 放宽条件需用户选择；工具超时 → 显示等待 / 查询状态；价格变化 → 再确认；恶意酒店描述要求泄露信息 → 将检索内容当数据，应用仍限制工具权限。教学页面应指出生产系统还需要日志、数据保护与错误恢复，不能把模型遵从提示词当作完整安全边界。

验收：播放正常与售罄路径；确认前不出现订单；工具失败后不显示成功；重复点击执行不会模拟两个订单；用户、智能体、模型、基础设施四个视角能对应到相同 request_id；读者能指出“模型提出、程序执行、酒店系统确认”。

## 模块 B：模型如何从一段输入生成一段输出

| 可点击步骤 | 输入 → 输出 | 解释与动画 |
| --- | --- | --- |
| 1. 构造提示 | 系统规则、会话、工具说明、用户消息 → 模型输入序列 | 展示拼装顺序；不是只有最后一句话占上下文 |
| 2. 分词 | 文本 → token ID 序列 | 用已固定并标注来源的 tokenizer 示例；中文一个字不必等于一个 token |
| 3. Prefill | 所有输入 token → 隐藏状态、各层 KV cache、下一个 token 的预测信息 | 先处理已有上下文，首次输出前通常要等待；不画成全网络完全无依赖地一次并行 |
| 4. 选择 token | 词表分数及采样规则 → 一个 token | 展示少量候选与“省略其余词表”；选择受温度等策略影响 |
| 5. Decode | 新 token 与已有 cache → 下一个 token 预测、cache 增长 | 自回归箭头逐步推进；一轮不保证恰好出现一个中文字 |
| 6. 停止与流式显示 | token 流 → 文本片段；终止条件 → 完成 | EOS、最大输出长度等停止；流式只是逐步展示，不等于提前知道完整答案 |

解释延迟时区分首 token 时间（TTFT）与生成阶段相邻 token 时间（ITL）。从客户端测得的延迟还含网络、排队、工具与检索；不要把它们全部叫模型计算时间。输出长度、输入长度、硬件、模型、批处理与调度都会改变结果。

验收：点击 prefill 后先出现 cache，再进入逐 token decode；输入与输出 token 数独立显示；重置清空演示状态；长输入场景解释首次等待，长输出场景解释累计生成时间。

## 模块 C：Q、K、V 与 KV cache 要留什么资源

先用检索比喻：“当前位置提出问题 Q，已有位置提供用于匹配的 K 和用于汇总的信息 V”，随后注明它们是从隐藏状态通过学到的投影得到的向量，比喻不等于模型在查询真实数据库。

点击顺序：隐藏状态 → Q/K/V 投影 → Q 与 K 计算相关程度（遮罩限制可看位置）→ 加权汇总 V → 后续层。再切换到生成下一 token：新位置产生 Q/K/V，读取之前缓存的 K/V，追加新 K/V。典型自回归 decoder 不需要把所有历史 Q 长期存入 KV cache；QKV 中间计算、attention 工作区和 KV cache 是不同资源。采用 GQA / MQA 时 KV 头数可能小于 Query 头数。

用于容量理解的简化关系：`KV 字节数 ≈ 2 × 层数 × KV 头数 × 每头维度 × 已缓存 token 数 × 每元素字节数`。多请求时对每个请求的有效缓存长度求和。假设每层配置相同、标准 decoder attention；不涵盖分块分配、对齐、量化元数据、缓存共享、滑动窗口或跨卡分片细节。模型权重、工作区、CUDA graph、通信缓冲与碎片也占显存，所以“剩余显存全部除以 KV 大小”不是可靠的最大并发承诺。

交互资源表：滑动输入长度、输出上限、同时活跃请求数、KV 精度，观察缓存预算；输出长度未生成时显示“准入预留策略”与“实际已用”两条线。区分每个请求已生成 token、允许的最大 token 与系统预留容量。标注这是容量估算，不是特定推理引擎的分配实现。

验收：固定其他条件后，增加实际缓存 token 应增加估算；改变 Query 头数但保持 KV 头数不变，不应按 Query 头数放大 KV；页面能回答“QKV 要预留多少”为何需拆为中间计算与长期 KV 缓存。

## 模块 D：一个模型如何服务很多人

点击步骤：请求到达 → 队列 / 准入 → 组成批次 → prefill → 生成步 → 已完成请求退出 → 新请求加入 → 继续生成。采用 continuous batching 教学例子：A 的输出长、B 的输出短，B 完成后位置可由 C 接替；说明实际调度可使用 token 预算、chunked prefill 等，图示不是所有引擎的统一实现。

默认同时展示三个数量：排队请求、正在处理请求、当前批次 token 预算。不要混用“在线用户数 / 同时请求数 / 活跃解码数 / 批大小”。提供“吞吐优先 / 延迟优先”两个教学策略，标注模拟结果；队列过长时超时或拒绝服务可见。

并发考虑清单：输入 / 输出长度分布、请求到达率、TTFT / ITL / 总延迟目标、模型权重与 KV 显存、计算与内存带宽、调度策略、工具 / RAG 延迟、前缀缓存命中与隔离、取消请求、服务配额。更多 GPU 未必等比例提升并发，跨卡通信与模型分片策略由基础设施模块解释。

误区：“GPU 放得下权重就支持无限多人”“batch 越大所有人越快”“连续批处理意味着输出无顺序”“并发就是 QPS”。必须给一个同 QPS、不同输出长度导致资源需求不同的示例。

验收：B 结束后 C 加入且 A 不丢失 cache；取消请求后释放对应模拟资源；批次满时新请求保持排队；图中的策略变化不宣称真实测得的性能提升。

## 模块 E：知识库一次 RAG 查询如何完成

RAG 拆成两个轨道。准备知识库先发生，用户查询时不会默认重新切分和 embedding 全部文档。

| 可点击步骤 | 输入 → 输出 | 必须解释 |
| --- | --- | --- |
| 准备 1：解析资料 | 原文档 → 可读文本与来源元数据 | 页码、章节、文档版本、访问权限要保留 |
| 准备 2：切分 | 文本 → chunks | 粒度与重叠影响召回和上下文；不是固定越小越好 |
| 准备 3：Embedding | 每个 chunk → 向量 | 同一兼容 embedding 空间与版本；向量不是原文的无损压缩 |
| 准备 4：建索引 | 向量、原文、元数据 → 索引记录 | 更新 / 删除、权限与版本同步，否则旧内容仍可能被检索 |
| 查询 1：接收问题 | 用户问题与身份 → 查询参数 | 权限用于检索过滤与后续结果检查 |
| 查询 2：查询编码 | 问题 → query 向量 | 可能另含关键词检索或查询改写；改写是可选步骤 |
| 查询 3：召回 | query 与索引 → 候选 chunks | top-k 仅表示取多少候选，不证明答案正确；过滤不能靠模型猜权限 |
| 查询 4：Rerank | 问题与候选文本 → 重排分数与较小候选集 | 许多 reranker 联合评估 query 与文本；可选，增加延迟，不是直接生成答案 |
| 查询 5：组装上下文 | 选中 chunks、来源、提示 → 最终提示 | 控制 token 预算、去重与覆盖；更多上下文不一定更好 |
| 查询 6：生成 | 最终提示 → 逐步输出答案与引用 | 跳转到 prefill / decode 模块；引用需对应可查看的来源 |
| 查询 7：检查与展示 | 答案、来源与规则 → 最终答复 | 无相关证据应说明不知道 / 追问；显示引用不自动证明句子被来源支持 |

点击例子：询问“这家酒店最晚几点可以取消？”知识库同时有新旧取消政策，展示版本过滤、召回、重排、证据选择与引用。对比无证据和冲突证据两个失败分支。酒店当天价格与库存应调用实时系统，不能默认相信知识库静态资料。

三条数据必须可追踪：原文 chunk、向量索引记录、进入提示的上下文。相似度分数与 rerank 分数不是置信度，也不应跨模型直接比较。恶意文档文本是外部数据，不能赋予工具执行权限。

验收：索引轨道与查询轨道分开；embedding 与 reranker、生成模型可为不同服务；点击回答引用能显示对应 chunk 与版本；未授权 chunk 不进入最终提示；取消 reranker 后仍可完整跑查询；无证据路径不编造取消条款。

## 联动与交付证据

一次酒店问题可联动全部模块：用户意图 → 查询酒店政策的 RAG → 搜索库存工具 → 用户确认 → 预订 → 答复。每次模型调用分别经历提示、prefill 与 decode，不把整个 Agent 循环当成一次模型推理。工具结果加入下一轮上下文会增加 token 与缓存需求；真实实现是否复用 cache 由推理服务决定。

内容审校交付：逐步输入 / 输出数据样例、术语表、正常与失败路径截图、键盘操作录屏或检查记录、教学模拟标签截图、引用核验记录、自测题及答案。技术验收应逐条记录通过 / 失败与证据位置；页面上线前由基础设施内容负责人复核资源估算边界，由测试角色核对状态转移。数据样例只能使用虚构个人与酒店信息。

自测题建议：谁真正创建订单？为何很长输入会增加首次等待？KV cache 保存什么？10 个长输出请求和 10 个短输出请求是否消耗相同资源？RAG 的向量检索结果为何还需要原文？来源缺失时能否给确定答案？
