# 课程地图：从一次业务请求理解 LLM 推理基础设施

状态：设计评审稿。核心读者是 Cisco 客户、合作伙伴、销售与售前工程师，具备网络、虚拟化或云平台运维背景，但没有 AI 背景。第一版为中文静态交互模拟，无真实 API；交互结果不是硬件实测或采购建议。

## 学习路线与共同场景

全课程用酒店预订串起业务、应用、模型与资源，再以运维知识库、业务高峰和故障排查迁移到读者的日常工作。运行视角统一为用户 `user`、智能体 `agent`、模型 `model`、基础设施 `infra`，不等同于职业角色。每章都先解释发生了什么与用户感受，再展开术语、计算或拓扑。

| 路线 | 推荐章节 | 读完能做什么 |
| --- | --- | --- |
| 理解与沟通 | 1 → 2基础层 → 3 → 4基础层 → 5 → 7概览 → 9概览 | 客户与销售能描述组件职责、体验目标、资源差异及需要进一步确认的问题 |
| 方案与工程细节 | 共享基础后依次完成 2–10 的工程层 | 伙伴、技术客户与售前能收集负载、做容量账本、检查通信与支持条件、制定验证和定位计划 |

所有角色可访问两条路线，不按职位锁定内容。M1 建立酒店、模型基础与单卡队列；M2 完成 RAG、KV容量、并发规划与GPU/UCS基础配置和证据对照；M3 深化多卡网络与GPU/UCS拓扑权衡，完成多模型与综合故障定位。每章的学习验收是后续试读与产品测试标准，当前不代表已通过。

## 第 1 章：一句“帮我订酒店”，谁真正完成工作？

- **读者问题：** 大模型能自己订房吗？Agent 是模型的新名字吗？什么情况下需要用户参与？
- **交互：** 严格沿用 [inference.md](inference.md) 模块 A 的八步：①接收意图 → ②整理约束 → ③应用检查 → ④查库存与价格 → ⑤比较候选 → ⑥用户确认 → ⑦应用执行预订 → ⑧告知结果。点击四视角看同一请求；切换缺字段、售罄、价格变化和超时分支。
- **输入输出：** 虚构日期、城市、人数与预算 → 验证参数 → 候选酒店与条款 → 用户确认记录 → 模拟订单状态 → 有依据的答复。没有成功工具结果不能输出预订成功。
- **学习验收：** 能指出模型提出调用、应用控制权限并执行、酒店系统确认订单；确认前不会出现订单；超时未知状态不能直接当作失败后重复下单。
- **前置 / 阶段：** 无 AI 前置；M1。工程层展开 request_id、tool_call_id、参数验证与幂等键，不要求基础层阅读 JSON。
- **专业文件：** [Agent八步与异常](inference.md)、[四视角与状态设计](../design/experience.md)、[目标读者](../product/audience.md)。

## 第 2 章：模型不是黑盒——token、配置、张量与 Dense / MoE

- **读者问题：** “8B”“上下文长度”“模型维度”分别是什么？输入文字怎样进入 GPU？MoE 的总参数与每 token 激活参数为什么不同？
- **交互：** 点击一句文本显示固定 tokenizer 的 token 序列，再点击教学模型配置卡：层数、隐藏维度、Query头、KV头、每头维度、词表、精度。逐层展开“token ID → embedding → 隐藏状态 → Q/K/V → attention → 后续计算 → 词表分数”。切换 Dense / MoE，显示后者路由到部分专家的示意。
- **输入输出：** 文本与模型配置 → token ID 与带维度标签的张量 → Q/K/V → 下一 token 预测。MoE 切换增加路由与专家执行示意，而不是改变酒店业务步骤。
- **学习验收：** 能说出参数是学到的权重、张量是带形状的数据；中文一个字不保证一个 token；QKV不是三个数据库；区分总参数、激活参数与部署显存。多数专家权重仍需驻留在所选部署资源中，不能仅用激活参数估算总权重显存。
- **前置 / 阶段：** 第1章；M1基础层、M2工程层。先画少量向量格子，再展开形状，不默认读者会线性代数。Dense每token使用其稠密网络；MoE通常只对MoE层选择专家，注意力及共享部分仍执行。具体头配置、路由、专家分布必须以模型为准。
- **专业文件：** [token和QKV](inference.md)、[术语表](glossary.md)、[容量与并行](infrastructure.md)。Dense/MoE配置和张量图需要新增到对应专业规格后审校；本地图不表示该细节已完成或已核验。

## 第 3 章：为什么先等一会儿，再逐字出现？

- **读者问题：** prefill 与 decode 做什么？“首字快”和“输出快”为什么是两个目标？
- **交互：** 构造提示 → 分词 → prefill → 选择token → decode循环 → 停止 / 流式显示。移动输入长度与输出上限，观察两个阶段及时间条；展开外部检索、排队、网络和工具等待。
- **输入输出：** 包含规则、历史、工具描述和用户消息的提示 → 输入token、KV cache与预测 → 输出token流 → 文本。一次Agent任务可能有多次这样的模型调用。
- **学习验收：** 能区分TTFT、ITL/TPOT和端到端任务延迟；长输入与长输出的影响不同；浏览器首字符时间与模型首token时间口径不同。
- **前置 / 阶段：** 第2章基础层；M1。公式和真实计时采集是工程层展开项。
- **专业文件：** [基础推理与指标](inference.md)、[体验口径](ucs-gpu-comparison.md)、[验证规格](../quality/validation.md)。

## 第 4 章：一张 GPU 上的模型怎样接待多人？

- **读者问题：** 每个用户都要一份模型吗？并发、QPS、batch 是不是一回事？长请求会不会堵住短请求？
- **交互：** 三个虚构用户进入队列，点击准入、prefill、decode；短请求完成后新请求加入连续批次。切换吞吐优先 / 延迟优先、取消请求与突发到达，观察队列和活跃请求。
- **输入输出：** 请求到达率、长度分布、调度预算 → 排队与活跃序列 → 输出和完成状态。模型权重可共享，但请求上下文与缓存须正确隔离。
- **学习验收：** 能区分在线用户、在途请求、活跃解码序列、批大小与QPS；解释批处理可以提高资源利用但不保证每个请求更快；指出GPU利用率不能单独判断体验。
- **前置 / 阶段：** 第3章；M1基础队列、M2并发规划。
- **专业文件：** [continuous batching](inference.md)、[单卡服务与预算](infrastructure.md)、[验证规格](../quality/validation.md)。

## 第 5 章：运维知识库怎样回答问题，而不只搜索链接？

- **读者问题：** embedding、reranker与生成模型各做什么？知识库更新为何可能没有立刻生效？答案带引用就可信吗？
- **交互：** 两条独立轨道。建库：解析运维文档 → 切分 → embedding → 索引。查询：问题及身份 → 查询编码 → 召回 → rerank → 组装上下文 → 生成 → 检查引用。点击“交换机告警如何排查”的固定样例，查看新旧版本、授权过滤、无证据和冲突证据分支。
- **输入输出：** 带来源、版本和权限的虚构运维资料 → chunk与索引；用户问题 → 候选片段、重排结果、提示 → 引用原文的回答。酒店政策查询作为前章联动，但当天库存、价格走实时工具概念路径。
- **学习验收：** 能把索引准备与每次查询区分；向量不是原文无损压缩；reranker不负责生成答案；相似度不等于正确概率；无证据时应说明不足。未授权内容不能进入最终提示。
- **前置 / 阶段：** 第1、3章；M2。
- **专业文件：** [RAG全过程](inference.md)、[读者运维迁移](../product/audience.md)、[来源与内容验收](../quality/validation.md)。

## 第 6 章：要预留多少显存，怎样算需要多少 GPU？

- **读者问题：** 模型放得下就能服务所有人吗？“QKV预留”应拆成哪些账目？
- **交互：** 每卡账本分为权重、KV、执行工作区、通信/框架开销与安全余量；调整输入长度、输出上限、活跃序列、KV精度，显示已用与准入预留。点击模型总参数、Dense/MoE、分片或副本，提示相应假设。
- **输入输出：** 明确模型配置、精度、长度分布、到达率、并发、延迟目标与硬件预算 → 容量可行性、必要分片 / 副本候选、待压测清单。输出不能承诺真实tokens/s或按显存直接宣称最大业务并发。
- **学习验收：** 能区分历史KV长期缓存与QKV计算中间量；用KV头数而非默认Query头数估算cache；说明权重容纳与性能达标是两项检查；GB/GiB和精度单位一致。显存不足方案显示不可行，不凭空给吞吐数字。
- **前置 / 阶段：** 第2、4章，RAG场景另需第5章；M2。
- **专业文件：** [KV机制](inference.md)、[GPU数量与每卡账本](infrastructure.md)、[虚构容量算例](ucs-gpu-comparison.md)。

## 第 7 章：模型跨卡后，每次生成在传什么？

- **读者问题：** 一机多卡与多机多卡为什么不同？NVLink、PCIe、RDMA和RoCE分别在哪一段？副本和模型分片有何区别？
- **交互：** 同一请求切换单卡、单机Tensor/Pipeline Parallel、多机分片及多副本。逐层/逐步点亮计算与通信，点击链路查看数据类型、同步点和范围；网络拥塞时标出等待。MoE的专家通信按所选并行方案展示，不能给所有架构套同一通信路径。
- **输入输出：** 模型分片策略、GPU/NIC拓扑、通信库、驱动与网络条件 → 数据传输及同步图 → 对首token、逐token等待与容量的影响解释。
- **学习验收：** 能解释多副本主要分担请求、模型分片合作完成模型；区分GPU显存带宽、机内互联和NIC链路；RoCE是基于以太网的RDMA技术路径，RDMA不自动意味完全绕过所有CPU工作；实际GPUDirect与传输路径需验证。
- **前置 / 阶段：** 第2、3、6章；M3。网络背景用于理解队列、带宽与拥塞，但术语仍首次解释。
- **专业文件：** [多卡与跨机通信](infrastructure.md)、[术语表](glossary.md)、[网络验证](../quality/validation.md)。

## 第 8 章：GPU代际与UCS配置，怎样变成客户能感知的差异？

- **读者问题：** 为什么不能只比较TFLOPS？更多显存、更高带宽与更强计算分别帮助什么？某GPU是否真能装入所选UCS？
- **交互：** 固定负载，切换教学显存预算及规格维度，点击“参数 → 生产影响 → 用户体验 → 限制”。真实GPU/UCS比较行只显示有来源的规格和支持状态；未核验行保留待核验，不生成伪排名。
- **输入输出：** UCS完整型号、GPU选件/形态、软件与供电散热条件、同口径规格、负载与SLO → 支持证据表、容量候选与实测计划。
- **学习验收：** 能区分GPU厂商规格与Cisco整机支持证据；计算精度和稠密/稀疏口径一致；不能用代际营销倍率换算用户响应或答案质量；不将候选型号视为采购结论。
- **前置 / 阶段：** 第3、6章支撑M2基础参数、容量与支持证据对照；第7章支撑M3机内/跨机拓扑与互联权衡深化。M2基础内容不依赖M3章节。
- **专业文件：** [GPU代际解释](infrastructure.md)、[UCS GPU比较与证据状态](ucs-gpu-comparison.md)。当前官方资料核验受网络限制；解除后由专业文档记录证据，课程不把受阻请求当已核验。

## 第 9 章：一个服务器或部署POD里有多个模型，怎样分资源？

- **读者问题：** 大语言模型、embedding、reranker可否共卡？共享、MIG、vGPU和多副本是同一种东西吗？
- **交互：** 把三类模型放入资源布局，切换独占卡、进程共享、受支持的分区等方案；模拟生成模型突发负载时检索服务受影响。点击“POD”先选择部署/机架资源域的含义，若指Kubernetes Pod另行标注，避免术语混淆。
- **输入输出：** 模型权重、负载、延迟目标、GPU支持与隔离要求 → 资源账本、调度/配额、争用和故障影响范围 → 部署候选。保留未选隔离方式的待确认条件。
- **学习验收：** 能说明time sharing不等于显存硬隔离；MIG/vGPU支持需核验；共享省资源可能引入邻居争用；副本容错与跨机分片故障范围不同。实际GPU显存不能按普通VM内存默认超配。
- **前置 / 阶段：** 第4–8章；M3。
- **专业文件：** [多模型分配](infrastructure.md)、[UCS共享支持条件](ucs-gpu-comparison.md)、[运维类比边界](../product/audience.md)。

## 第 10 章：用户说“AI变慢了”，先查哪里？

- **读者问题：** 怎样区分检索、工具、排队、计算、KV不足或通信问题？什么时候扩容，什么时候改配置或知识库？
- **交互：** 同一request_id的任务时间线与指标面板，点击证据后作定位选择。固定故障卡：RAG检索慢、工具超时、请求高峰排队、长输入prefill、长输出decode、KV压力、跨机通信拥塞、邻居模型争用、节点失效。每张卡至少有一个排除项和下一验证动作。
- **输入输出：** 阶段计时、长度分布、到达率、队列、GPU/显存、通信与工具状态 → 有证据的假设 → 下一检查 → 修复或降级候选。静态例子解释因果，不冒充现场诊断。
- **学习验收：** 不能仅凭GPU利用率或网络图判断瓶颈；区分模型调用和完整Agent任务指标；同模型突然变慢时能先比较负载与分阶段数据；指出节点故障下副本和分片恢复路径的区别。
- **前置 / 阶段：** 第1–6章支撑基础定位，第7–9章支撑综合定位；M3。M1/M2各章先内置局部异常，M3再汇成完整运维演练。
- **专业文件：** [阶段机制与异常](inference.md)、[资源与通信](infrastructure.md)、[目标读者运维问题](../product/audience.md)、[验证计划](../quality/validation.md)。故障面板字段与诊断场景仍需具体设计评审。

## 交付与评审门槛

每章交付一张完整流程图、可复现固定输入输出、正常和失败状态、基础/工程分层文本、一题自测及答案、来源与待核验状态。播放、暂停、单步、重置、键盘和减少动效都应可用；不能靠动画颜色承载唯一信息。专业文档提供技术细节，本地图只负责顺序、依赖与学习目标，不替代规格。

评审优先检查：酒店八步与专业文档一致；所有示例明确模拟；术语首次解释；公式单位与假设公开；未知硬件支持不被补成推测；沟通路线无需代码与公式可完成。至少由偏沟通和偏方案的两类目标读者试读，再记录能否解释并迁移到实际问题。内容审校、交互测试与目标读者试读分别留证，不能相互替代。

后续内容缺口：[术语表](glossary.md)已有Dense/MoE与张量的文字解释，尚需固定教学模型配置、可点击结构图和逐步输入输出的结构化交接；另外还需运维RAG固定样例、故障定位案例与面板、具体UCS/GPU核验表。由对应专业文档负责人落实，不以本课程地图新增章节描述冒充已开发内容。
