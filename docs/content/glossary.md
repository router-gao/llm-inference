# 常见术语与性能指标

当前读者定位：有网络与IT背景、缺少AI背景的思科客户、合作伙伴、销售及售前工程师；按[读者规范](../product/audience.md)组织基础与工程解释。此前宽泛的读者称呼以本条为准。

状态：教学初稿，待技术来源核验与试读。所有数字是示例，不是性能实测。适用于常见自回归文本生成；具体框架定义可能不同。

## 页面解释规则

首次出现术语就提供一句中文解释，可点击展开例子、工程定义、单位、测量起止点和误区；另提供可搜索术语页。指标必须说明客户端还是服务端测量，是否包含排队、网络、检索与工具时间。基础层不要求理解公式才能继续。

## 一次推理中的词

| 术语 | 通俗解释 | 例子与边界 |
| --- | --- | --- |
| 推理 Inference | 用已经训练好的模型处理输入、生成结果 | 区别于修改模型参数的训练；一次 Agent 任务可能调用模型多次 |
| Token | 模型处理文字的小单位 | 不等于一个字或单词；中英文、数字及所用 tokenizer 都影响切分 |
| Tokenizer 分词器 | 在文字与 token ID 之间转换的工具 | 输出 token 到界面字符还涉及解码和显示 |
| Context 上下文 | 这次调用提供给模型的历史与资料 | 用户消息、系统规则、工具说明、检索资料等均可能占用 token |
| Context window 上下文窗口 | 模型一次处理所支持的序列长度范围 | 输入加输出受模型与服务限制；允许长上下文不表示成本不变 |
| Prefill 输入预处理阶段 | 模型先处理已有输入，为生成准备状态 | 长提示通常增加首 token 等待；它不是知识库检索，也不是加载权重 |
| Decode 自回归生成阶段 | 根据已有上下文逐步预测后续 token | 普通解码逐 token 推进；推测解码等优化可能一次接受多个 token |
| Q / K / V | 注意力里用于匹配和汇总信息的三组向量 | Q 像当前位置的问题，K 像匹配线索，V 像可汇总信息；不是自然语言问题和真实数据库 |
| KV Cache | 保留之前位置的 K/V，避免下一步重复计算 | 通常不长期缓存所有历史 Q；不同请求的缓存状态需要隔离 |
| Attention 注意力 | 让当前位置按相关程度使用可见位置的信息 | 是数值计算；不等同于人的注意或事实检索 |
| 模型权重 | 训练得到、推理时使用的参数 | 多用户可共享权重，但各自上下文与缓存不同 |
| 精度 / 量化 | 用不同数值表示方式存放或计算数据 | 权重精度、计算精度、KV 精度可不同；低比特不保证质量和速度不变 |

## 怎么看一个模型的配置

“这个模型多少维”需要先问指的是哪个对象：token的隐藏向量、embedding输出，还是某个权重张量。模型不是只有一个维度数字。以下以常见Transformer为例，其他架构可能不同。

| 术语 / 配置字段 | 通俗解释 | 例子与常见误区 |
| --- | --- | --- |
| Parameter 参数 / 参数量 | 训练得到的数值；参数量是这些数值的数量 | 8B约为80亿个参数，不是80亿维，也不是文件大小；运行配置参数与模型权重参数需分开 |
| Dense 稠密模型 | 常见用法指没有按token路由到部分专家的模型 | 通常每个token使用同一组主要模块；不表示每个权重数值非零，也不表示每次推理都读取全上下文 |
| Sparse 稀疏 | 泛指只使用或保留部分连接、数值、专家或注意力关系 | 必须说明稀疏在哪里：MoE、权重剪枝和稀疏注意力不是同一回事 |
| MoE：Mixture of Experts，混合专家 | 某些层设置多个专家，由路由器为每个token选择部分专家 | 专家通常是前馈子网络，不是独立聊天机器人；可以与稠密模块共存 |
| Expert / Router / Top-k routing | 专家负责计算；路由器决定该token交给哪些专家；top-k是选几个 | 8个专家每token选2个，不代表整个模型只用四分之一；共享模块和共享专家也可能参与 |
| 总参数 / 激活参数 | 全部权重数量 / 某次token计算涉及的参数数量 | MoE可有很多总参数而较少激活参数；激活参数少不等于只需存放这些权重，普通GPU部署仍需考虑全部专家或明确卸载方案 |
| Scalar 标量 | 一个数 | 如单个得分；在常见数学约定下是零阶张量 |
| Vector 向量 | 一串有序数 | 一个token可表示为4096个数；不是4096个token |
| Matrix 矩阵 | 按行和列排列的数 | 形状4096×4096的矩阵含16777216个数 |
| Tensor 张量 | 可有多个轴的数值数组 | 标量、向量、矩阵都是特例；这里先讲机器学习里的数组含义，不要求数学推导 |
| Shape 形状 / Axis 轴 / Rank 阶数 | 每条轴的长度 / 数据的组织方向 / 轴的数量 | `[2,128,4096]`是三阶张量，三条轴可表示批次、token位置和隐藏特征；rank在矩阵秩或LoRA中有另一种含义 |
| Dimension 维度 | 可指轴的数量，也可指某条轴的长度，需说明语境 | “4096维向量”指4096个分量，不是4096条轴；不要把shape与参数量混用 |
| Hidden size / d_model 隐藏维度 | 每个token在模型主干中常用的特征宽度 | 4096表示每个位置的隐藏向量有4096个分量；更宽不自动代表更聪明 |
| Embedding dimension 向量维度 | embedding输出向量的分量数 | 知识库向量可为1024维，与生成模型hidden size不必相同；维度相同也不保证属于兼容空间 |
| Layers / num_hidden_layers 层数 | 模型依次经过多少个主要计算块 | 32层不是32张GPU，也不是回答32次；具体计数以架构配置为准 |
| Attention heads 注意力头 | 将注意力计算分成多个子空间 | 32个头不是32个模型或32个用户槽位 |
| Head dimension 每头维度 | 单个注意力头的向量宽度 | 常见架构中4096隐藏维度÷32个query heads=128；不同架构可能显式指定，不普遍套用 |
| KV heads / GQA / MQA / MHA | K/V使用多少头；不同方案让query heads与KV heads有不同共享关系 | MHA常见query与KV头数相同；GQA多组query共享较少KV头，MQA常见只有1个KV头。直接影响标准KV预算 |
| Intermediate size / FFN 前馈宽度 | 前馈模块内部的特征宽度 | 通常不同于hidden size；门控FFN和MoE改变权重组成，不能只乘一个矩阵算总参数 |
| Vocabulary size 词表大小 | tokenizer/模型支持多少token类别 | 不等于模型知道多少词或事实；可能还有保留token与填充对齐 |
| Dtype 数据类型 | 每个数如何表示，例如FP32、BF16、FP16 | 常见BF16与FP16每个元素2字节，但数值范围不同；量化存储还需元数据 |
| Architecture 模型架构 | 模块如何连接与执行 | 参数量相同的模型可能有不同层数、宽度、注意力方式、专家和资源需求 |

### 一个配置例子：数字分别说明什么

这是虚构的常见decoder结构示例，不对应已核验的具体模型：32层、hidden size 4096、32个query heads、8个KV heads、head dimension 128；2条输入序列，每条128个token，采用BF16。

- 隐藏状态形状可写为 `[2,128,4096]`：2条序列×128个位置×每位置4096个数。共有1048576个元素，BF16裸数据约2 MiB，不等于整个模型运行内存。
- 投影后的一种示意排列：Q为 `[2,128,32,128]`，K/V各为 `[2,128,8,128]`。运行库可以采用不同轴顺序、分片和存储布局。
- 标准未分片KV缓存覆盖32层和这256个位置时，裸数据为 `2×32×8×128×256×2` 字节，即32 MiB。前面的2表示K与V；最后的2是每元素字节数。
- 一块4096×4096权重矩阵有约1678万个参数，BF16裸数据32 MiB；它只是一块权重，不是整个模型。
- 总参数量必须结合词表、层内投影、前馈、专家、参数共享等实际结构统计，不能仅从hidden size或层数猜出。

页面交互：点击张量的三个轴分别高亮“几条请求 / 几个token / 每个token多少特征”；切换GQA观察K/V变窄；切换Dense/MoE观察专家路由、总权重存储与激活计算的区别。使用“同样参数量不等于同样吞吐”的反例，避免把数字大小解释成质量排名。

## 请求与并发

| 术语 | 通俗解释 | 测量或误区 |
| --- | --- | --- |
| 并发 Concurrency | 同一时刻尚未结束的工作数量 | 必须说明统计业务任务、服务请求还是活跃模型序列；在线用户数不是并发推理数 |
| 到达率 | 每秒有多少新请求进入 | 单位 requests/s；不是系统实际完成量 |
| QPS / RPS | 每秒处理多少查询或请求 | 明确计收到、完成还是成功的请求；RAG 查询与一次模型调用不一定一一对应 |
| Batch 批次 | 放在一起处理的一组序列或 token | batch size 的口径可能是序列数，也可能涉及 token 预算 |
| Continuous batching 连续批处理 | 请求完成后，调度器可让新请求加入后续计算 | 不必等原来整个批次全部结束；不代表无排队 |
| 调度 Scheduling | 决定哪个请求何时获得计算与缓存资源 | 会影响吞吐、公平性和首 token 等待 |
| 排队时间 | 请求已到达但尚未获安排的等待 | 应分清准入队列与模型执行队列，不能一概算成GPU计算 |
| 限流 / 准入控制 | 控制进入系统或进入执行的工作量 | 资源不足可排队或拒绝；避免无限积压 |
| 冷启动 | 服务或模型尚未就绪时的初始化成本 | 包括加载权重、运行时准备等；与每次 prefill 分开 |
| 前缀缓存 | 复用相同输入前缀的已计算状态 | 命中依实现、缓存容量与隔离策略；不等于复用完整答案 |

## 延迟与吞吐

“首字符延迟”和“首 token 延迟”不完全相同：用户看到的是字符，模型输出的是 token，流式传输又可能把多个 token 合为一块。

| 指标 | 读者问题与定义 | 单位 / 口径 |
| --- | --- | --- |
| TTFT：Time To First Token，首 token 延迟 | 发出请求后，多久收到第一个输出 token？ | ms 或 s；客户端测量可含网络、排队、prefill及缓冲。若只观察流式chunk，应标记为首块延迟而非假称逐token测量 |
| 首字符显示延迟 | 多久在页面看到第一段可见文字？ | ms 或 s；还可能含解码、传输缓冲与前端渲染，空内容/元数据块不算文字 |
| ITL：Inter-Token Latency，token 间延迟 | 连续两个输出 token 相隔多久？ | ms/token；需要真实token时间戳，不能用字符间隔代替 |
| TPOT：Time Per Output Token，平均每个输出 token 时间 | 首 token 之后，平均生成节奏如何？ | 常用 `(最后token时间−首token时间)/(输出token数−1)`；输出只有1个token时此公式不适用。框架可能采用其他口径，必须注明 |
| E2E latency：端到端延迟 | 从发请求到整个结果完成多久？ | s/request；说明终点是最后token、结束事件还是界面渲染，Agent任务还可能包含多轮调用和工具等待 |
| Token throughput：token吞吐 | 系统每秒完成多少 token 工作？ | tokens/s；分别注明输入、输出或合计，整服务还是单请求，测量时段与并发 |
| Request throughput：请求吞吐 | 系统每秒完成多少请求？ | requests/s；注明成功/失败、请求长度分布及延迟目标 |
| Goodput：有效吞吐 | 满足约定质量/延迟要求的完成量 | 可用 requests/s 或 tokens/s，但必须定义合格标准；快而超时的结果未必计入 |
| P50 / P95 / P99 延迟 | 大多数请求快不快，最慢一批有多慢？ | P95 表示约95%的样本不超过该值；不是平均值，需注明样本数、时段和指标 |
| SLO：服务目标 | 我们承诺多快、多可靠？ | 例：95%请求TTFT≤2秒；示例目标，不是本项目实测 |
| 超时率 / 错误率 | 有多少请求没在期限内完成或失败？ | 百分比；定义分母、错误类型及是否包含重试 |

### 一个可点击的时间线示例

请求在0秒发出；第一个token在0.8秒收到，第二个在0.9秒，第三个在1.1秒，第四个在1.2秒。

- TTFT = 0.8秒。
- ITL分别为0.1、0.2、0.1秒；平均不代表每个间隔相同。
- 上述口径TPOT = (1.2−0.8)/(4−1) ≈ 0.133秒/token。
- 若以最后token为终点，E2E = 1.2秒；服务结束事件晚到则另一口径更长。
- 4/1.2≈3.33 tokens/s是该请求包含首次等待的输出速率，不是系统满载吞吐；首token后的平均生成速率约7.5 tokens/s。

实现时读者点击时间线标记，显示指标的起点、终点和计算。数字来源保持“固定教学示例”。

## GPU、通信与知识库术语

| 术语 | 一句话解释 | 边界 |
| --- | --- | --- |
| 显存 VRAM / HBM | GPU存放权重、缓存和临时数据的空间；HBM是一类高带宽存储技术 | 容量和带宽是不同指标，GB与GiB需区分 |
| 内存带宽 | 每秒能搬运多少数据 | GB/s；不是网络速度，也不是计算能力 |
| 算力 FLOPS | 每秒可执行多少浮点运算 | 与数据精度和计算模式相关；峰值不等于实际推理吞吐 |
| GPU利用率 | 某测量工具看到的设备忙碌程度 | 不等同于显存占用或达到峰值算力；必须注明工具与采样定义 |
| TP 张量并行 | 同一层的计算拆到多张卡 | 需要层内通信，具体通信依实现 |
| PP 流水线并行 | 不同层或阶段放在不同卡 | 阶段之间传数据，可能等待和不均衡 |
| 模型副本 / DP | 多份模型分别处理不同请求 | 通常提升总容量，不自动加速单请求；区别训练数据并行 |
| PCIe / NVLink / NVSwitch | GPU及设备的机内连接通路或交换设施 | 可用性取决于硬件拓扑；不是所有服务器都有NVLink |
| NCCL | 多GPU协作时常用的通信库 | 按环境使用不同传输，不是物理网线 |
| RDMA | 远程直接内存访问能力 | 需要软硬件支持，不代表完全没有CPU参与或通信成本 |
| RoCE | 在以太网上提供RDMA的技术 | 不是RDMA的全部；配置与拥塞影响收益 |
| InfiniBand | 常用于高性能互联的网络技术 | 可提供RDMA，与RoCE区别说明 |
| GPUDirect RDMA | 支持时让网卡直接访问GPU内存 | 依赖硬件、驱动和拓扑支持 |
| Node / Pod | 节点是机器；Kubernetes Pod是同节点上运行的一组容器 | “集群Pod”可能另有厂商定义，不与Kubernetes Pod混用 |
| MIG / Time slicing | 支持的GPU硬件分区 / 多工作时间共享 | 时间共享不保证显存硬隔离 |
| Embedding | 将文本等数据映射为用于匹配的向量 | 不是原文无损压缩；兼容空间与版本很重要 |
| Chunk | 知识库切分后的一段资料 | 要保留来源、版本和权限 |
| 向量检索 / Top-k | 依据向量匹配取候选 / 取候选数量 | 相似度不是答案正确率 |
| Reranker 重排器 | 对问题与候选资料重新评分排序 | 可选；通常不是最终答案生成器 |
| RAG | 先检索资料，再把资料交给生成模型回答 | 检索、生成和引用都可能出错；不保证无幻觉 |
| 幻觉 | 输出了没有依据或错误的内容 | 流畅与有引用不证明真实正确 |
| Tool calling 工具调用 | 模型提出结构化调用，由应用检查和执行工具 | 生成调用不等于业务操作已成功 |

## 内容与实现验收

1. 首次出现有解释，术语页与场景解释一致，支持鼠标和键盘。
2. 每项性能指标显示单位、统计对象、测量起止点、样本/窗口和模拟或实测标签。
3. 能通过时间线看清TTFT、ITL、TPOT与端到端延迟的区别；token不替换为字符。
4. 并发、到达率、QPS、吞吐与batch分开讲，用长短输入输出反例说明区别。
5. 平均、P95/P99、单请求与整服务口径不可混用；一token和零输出等边界显示“不适用”或单独说明。
6. 发布前依据框架官方指标定义及模型文档核验，记录版本与来源。当前未完成外部来源核验或页面测试。

新增验收：读者能分辨参数量、隐藏维度、张量形状与阶数；能解释Dense/MoE及总参数/激活参数区别。模型实例发布前核验官方config、架构说明和字段含义；本节目前是教学初稿。
