# GPU起源与基础架构：为什么它适合AI

状态：新增内容设计，待用户review与来源核验。面向网络、虚拟化和云运维背景、没有AI基础的Cisco读者。按直觉→组件→生产与体验组织，不要求微体系结构知识。

## 1. 起源：从图形处理到通用并行计算

GPU的技术脉络来自显示、图形与3D加速：很多像素、顶点等工作可以并行处理，推动专用图形硬件发展。后来可编程着色器和通用GPU计算工具让其承担图形以外的并行任务；深度学习中的大量矩阵运算和数据并行适合利用这类能力。

不能把GPU写成最初专为AI设计。现代GPU增加面向矩阵等计算的专门能力，也仍有不同产品定位。GPU没有单一无争议的“发明时刻”；图形加速器的演进、GPU命名/营销节点、通用计算和AI应用应分开。

可点击时间轴采用阶段而非未经核验的精确年份：图形加速→可编程图形→通用GPU计算/CUDA生态→深度学习应用→矩阵加速与数据中心系统。具体年代、产品及“第一”类说法，发布前查官方或可靠历史资料；CUDA属于NVIDIA生态，不是所有GPU通用的软件接口。

## 2. 基础结构：一次token计算用了哪些部件

| 组件 / 概念 | 通俗解释 | 生产与用户体验关联 |
| --- | --- | --- |
| CPU与GPU | CPU擅长灵活控制与多类任务；GPU提供大量并行计算资源 | 应用/调度/工具仍常由CPU参与；GPU快不代表完整任务快 |
| SM等计算单元 | NVIDIA GPU中承载线程执行的主要组织单元；其他厂商命名不同 | 并行资源要有足够工作及合适内核才能利用，不能按SM数量直接推算tokens/s |
| CUDA cores / 普通运算执行资源 | 执行各类算术指令的资源，具体能力依架构 | 厂商“core”数量不是可与CPU核心直接一一比较的单位 |
| Tensor Cores等矩阵加速单元 | 针对受支持数据类型/形状执行矩阵相关计算 | 常服务模型算子；内核、精度、batch和架构支持决定实际收益 |
| SIMT / Warp | 多线程按分组方式执行；NVIDIA常用warp概念 | 分支、访存和工作布局影响效率；不是每个用户固定占一组warp |
| Registers / Shared memory | 计算单元附近的小容量存储；后者在合适范围内供线程协作 | 容量与使用方式影响内核效率，不等于模型KV主存储池 |
| Cache（如L2） | 自动或受机制影响地复用部分数据的硬件缓存 | 与软件管理的KV Cache名称相似但不是同一层东西 |
| 显存 / HBM或GDDR | 放权重、KV和运行数据的设备内存 | 容量决定是否容纳，带宽影响搬运；不是所有GPU都用HBM |
| Memory controller / 数据通路 | 将计算单元和内存连接起来 | 数据搬运可能让计算单元等待，峰值算力不一定被用满 |
| PCIe / NVLink及NIC | 主机与设备、支持时GPU间、跨机网络的数据通路 | 具体拓扑影响加载和多卡通信；不是所有GPU/服务器都有相同能力 |
| Kernel / Stream | 软件提交的计算任务 / 有顺序约束的工作队列 | 异步执行不代表所有操作都同时发生；依赖与资源仍可能等待 |

图示应给读者一条完整路径：应用准备请求→运行时提交算子→GPU计算单元读权重/状态→执行矩阵与注意力等运算→写更新状态/结果→返回输出。明确模型的层、heads和张量是软件结构，不与SM、硬件core一一对应。

## 3. 为什么“算力很高”仍会慢

展示三种教学瓶颈：计算任务很多、需要搬运的数据很多、跨设备等待很多。prefill常较有利于并行矩阵计算，小批量decode可能更多受内存带宽影响，但这不是所有模型/负载的固定规律。增加并发可能改善利用率，也会增加KV和排队压力。

用同一请求点击“算”“搬”“等”，连接TTFT、输出间隔和总延迟；不从纸面FLOPS计算真实出字速度。GPU利用率、显存占用、算力利用和服务吞吐分别解释。

M1提供CPU/GPU、计算/显存、模型软件结构与硬件区别的基础图；M2扩展内存层级、矩阵单元与算/搬瓶颈；M3连接互联拓扑。历史时间轴作为可选阅读，不成为主流程前置。
