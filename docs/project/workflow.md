# 项目管理与团队分工

## 已确认决策

- 目标：中文、以读者理解为中心的可点击 LLM 推理学习网站。
- 读者：具有网络与IT背景、没有大模型与AI背景的思科客户、合作伙伴、销售与售前工程师。
- 分层表达：默认以业务场景及熟悉的网络/IT概念解释；按需展开公式、部署和通信细节。
- 第一版：静态前端、模拟数据；不调用真实模型、酒店或支付 API。
- 当前阶段：v0.2整体设计及用户review；尚未实现产品或运行产品测试。

## 文档与开发流程

1. 需求：产品文档定义目标读者、用户故事和验收条件。明确模拟范围。
2. 内容：每个模块定义读者问题、点击步骤、输入输出、来源、简化边界。
3. 设计：将内容映射成页面、共享场景状态和交互动作；先审查一条完整旅程。
4. 评审：项目负责人整合；QA 核对事实与可验收性。分歧记录为决策，不暗中改范围。
5. 实现：按任务板分配独立模块；实现者更新状态、关联变更和测试证据。
6. 验收：运行功能、计算边界、可访问性检查；产品检查读者是否能解释流程。
7. 发布：记录版本范围、已知限制和运行说明。真实接口接入属于单独迭代。

每项任务至少记录 ID、负责人、输入文档、依赖、交付物、验收条件、状态、验证证据。状态为待办、进行中、待评审、完成、阻塞。文档写完只代表交付，不等于产品实现完成。

## 变更与事实管理

- 需求变化先更新需求与决策，再更新设计、任务和验收。
- 内容来源标明 URL、适用版本、核验状态；未经读取的链接不能标为已核验。
- 计算示例说明单位和假设；显存可容纳不代表满足吞吐或延迟目标。
- 区分 QKV 计算和 KV Cache、服务器与 Kubernetes Pod、模拟结果与实测结果。
- 酒店流程展示授权与最终确认，不把演示按钮解释为真实订单。
- 每次阶段报告注明完成、未执行和阻塞事项。

## 版本顺序

- M0：需求、内容结构、交互方案、测试计划和任务板。
- M1：完整的酒店预订模拟，串起用户、Agent、模型和资源视角；提供最小推理机制说明。
- M2：RAG 查询流程、单卡并发、GPU 显存估算与参数交互。
- M3：单机多卡、跨机通信、RDMA/RoCE 和多模型资源分配。

所有用户提出的主题均纳入路线；分版本交付用于降低一次性复杂度，不删除后续主题。各专业文档的范围建议由本表统一排期。

## 大需求先预研

用户已授权：需求较大或涉及多方案/外部核验时，先输出需求或功能预研，见[预研入口](../research/README.md)。先保留用户要求及关联编号，完成场景、来源、候选/取舍、依赖、验收和分期建议，再讨论入选范围。选定后同步正式PRD、课程、设计、任务和排期；不能把候选直接当已批准交付，也不能遗漏原要求。简单明确的修改直接推进。灵感随手记不自动进入预研。

## 遗留问题与Release Notes

持续维护[遗留问题台账](open-issues.md)，记录问题ID、类型、影响、主责、下一动作、状态和关闭证据。建议每周及里程碑前讨论，具体时间待约定；不自动发送消息/安排会议。每次交付更新[Release Notes](../../RELEASE_NOTES.md)，区分文档、预览和正式产品，列实际验证与已知ISS。用户批准、Git推送和部署必须分别有证据，不以版本名代替。
